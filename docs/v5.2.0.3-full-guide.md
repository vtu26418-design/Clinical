# Clinical Trial Intelligence Workbench v5.2.0.3

## 1. What to open first

The ZIP includes the built React interface, FastAPI source, PostgreSQL configuration, tests, the frozen 800-record public registry cohort, verified saved models and this operating guide. PostgreSQL holds accounts, sessions, projects, memberships, chat, feedback and research metadata. Source files and model artifacts remain on persistent disk. There is no SQLite fallback.

Start in this order: prepare the environment; start PostgreSQL and the workbench; create an owner account; create/open a project; load the starter cohort; inspect Overview; use Prediction Studio. Training is an independent owner workflow and is not required for the bundled predictions.

The main navigation is Overview, Studies, Prediction Studio, Protocol Evidence, Scenarios, Models, Assistant and Settings. More tools contains Data Manager, Experiments, Validation Lab, the evidence animation pages, Phase Academy, Research sources, Saved library and Access Control.

## 2. Windows startup without Docker

Use the full ZIP on a Windows computer. Python 3.12 and native PostgreSQL are required. Docker and Node are unnecessary when using the included prebuilt interface. Internet is needed to install Python dependencies and for optional live sources/assistant providers.

### Install the prerequisites

1. Download Python 3.12 from [the official Python Windows downloads page](https://www.python.org/downloads/windows/). Select a Python 3.12 Windows installer matching your computer. Include the Python launcher; the launchers use `py -3.12`. Adding Python to PATH is convenient but does not replace the launcher.
2. Download PostgreSQL through [the official PostgreSQL Windows page](https://www.postgresql.org/download/windows/). Install the server and command-line tools. pgAdmin is optional for this workbench.
3. During PostgreSQL installation choose a strong password for its administrator role `postgres`. Remember it privately. Keep the selected port, usually 5432. This password is separate from the application database password and your workbench account password.
4. In Windows Services confirm the installed PostgreSQL service is running. The application will connect to it; the workbench launcher does not install or start that Windows service.

### Extract, set up, connect and start

1. Download the complete v5.2.0.3 Workbench ZIP. Right-click → Extract All into a writable local directory such as `C:\CTI`. Open the extracted directory containing `SETUP_WINDOWS.bat`; do not run inside the ZIP viewer.
2. Double-click `SETUP_WINDOWS.bat` once. Wait for successful dependency installation. It creates `.venv`, prepares your private `.env` and generates application credentials plus the first-owner `SETUP_TOKEN`.
3. Double-click `CONNECT_DATABASE_WINDOWS.bat`. For a new local installation press Enter for host `127.0.0.1`, port `5432`, application role `cti` and application database `cti`. Press Enter at the application-password prompt to keep the generated private password. If your PostgreSQL installation uses another port, enter it.
4. Accept administrator role `postgres` and maintenance database `postgres`. Enter the administrator password chosen during PostgreSQL installation at the hidden prompt. The helper uses Python `getpass`; password characters are not displayed and the administrator password is not saved.
5. Wait for **Application database login verified.** The helper creates only missing roles/databases, leaves existing role passwords and database contents intact, and writes `DATABASE_URL` only after verifying application login. It does not reset data or run application schema operations.
6. Double-click `START_WINDOWS.bat`. Leave the terminal open and visit `http://localhost:8000`, or the local address/port printed by your configured server. The application performs its normal initialization on start.
7. Open your local `.env` in a text editor and copy only the value after `SETUP_TOKEN=` into the first-owner form. Enter your name, email and a unique account password of at least 12 characters. Do not share `.env` or paste its full contents into chat.
8. Create a project, open it, choose More tools → Data Manager and load the 800-record starter cohort. Select that dataset. Review Overview and run Prediction Studio with a bundled approved model.

Equivalent PowerShell commands, from the extracted project root:

```powershell
py -3.12 scripts/setup.py
.venv\Scripts\python.exe scripts/configure_postgres.py
.venv\Scripts\python.exe scripts/start.py
```

### Subsequent starts and existing installations

On later visits keep PostgreSQL running and use `START_WINDOWS.bat`; repeat setup only to install/refresh dependencies. Close the server with Ctrl+C when finished. Stored projects remain in PostgreSQL and source/model files remain under persistent storage.

`CONNECT_DATABASE_WINDOWS.bat --check` performs a read-only login check with no credential prompts or file changes. `--configure` deliberately selects other connection settings. A working existing URL is verified and preserved without administrator prompts. Unavailable remote URLs are preserved; explicit remote reconfiguration requires typing `CONFIGURE`. Existing URL options, including TLS/certificate settings, remain defaults.

If the application role already exists with another password, the helper refuses to reset it. Enter its known password or choose a new role. Creation needs an administrator with CREATEROLE and CREATEDB. Partial creation can leave a missing object created before a later failure; retry safely reuses it. Only `DATABASE_URL` changes after success; unrelated secrets, `COMPOSE_DATABASE_URL` and `SETUP_TOKEN` are retained.

## 3. Linux/macOS and optional Docker

### Native Python and PostgreSQL

Install Python 3.12 and a running PostgreSQL service using your operating system's supported installer/package manager. Use the extracted project root:

```bash
python3.12 scripts/setup.py
.venv/bin/python scripts/configure_postgres.py
.venv/bin/python scripts/doctor.py
.venv/bin/python scripts/start.py
```

The connector follows the same hidden-password, create-missing-only behavior as Windows. For a managed remote database use its operator-provided PostgreSQL connection and TLS settings. Open `http://localhost:8000`, use your local setup token and create the first owner. Node is unnecessary with the included built interface.

### Optional Docker workflow

On Windows install/start Docker Desktop with its Linux-container engine and any required WSL2 configuration. With Python 3.12 installed, double-click `START_DOCKER_WINDOWS.bat`. On Linux/macOS install Docker with Compose and use:

```bash
python3.12 scripts/initialize_env.py --start
```

Or prepare the environment and start explicitly:

```bash
python3.12 scripts/initialize_env.py
docker compose up -d --build workbench
docker compose ps
```

Docker builds the application and starts its PostgreSQL service. The first build can take several minutes. Keep Docker running. Stop with `docker compose down`; retain named volumes. Removing volumes deletes stored data. Native Windows users can complete the entire research workflow without Docker.

### Frontend development only

Install Node.js 22, run `npm ci` then `npm run dev` inside `frontend/`, with the backend running on port 8000. `npm run build` regenerates `frontend/dist`. End users do not need Node because the release contains built assets. `scripts/setup.py --dev` installs Python test dependencies; see chapter 15 for a separate test database.

## 4. Environment values

Initialization prepares a private `.env` from `.env.example`, generating local database credentials and a setup token while preserving existing operator values. Credentials are excluded from release ZIPs. The native connector writes only a verified `DATABASE_URL`.

Use secrets only in your local server environment or managed secret store. Do not use `VITE_` variables for credentials: frontend variables can become public browser assets. Restart the server after environment changes. Never publish `.env`, passwords, provider keys, sessions, runtime logs or databases.

| Variable | Purpose |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD` | Local Docker database credentials; the password is generated. |
| `POSTGRES_PORT` | Native database port, normally 5432. |
| `DATABASE_URL` | Native application's PostgreSQL connection. |
| `COMPOSE_DATABASE_URL` | Container PostgreSQL connection, normally using hostname `postgres`. |
| `TEST_DATABASE_URL` | Disposable test database, normally port 5433 and database `cti_test`. |
| `SETUP_TOKEN` | Generated first-owner setup secret. |
| `APP_ENV`, `AUTH_MODE` | Development/production environment; use authenticated `session` mode. |
| `AI_PROVIDER`, `AI_PROVIDER_PRIORITY` | Assistant provider preference. |
| Provider key and model fields | Server-side credentials and an API model ID your account can access. |
| `AI_MAX_OUTPUT_TOKENS`, `AI_CONTEXT_CHARS` | Server response/context ceilings. |
| `TRUSTED_PROXY_HOSTS` | Explicit trusted proxy IPs/CIDRs; empty ignores forwarding headers. |
| `RATE_LIMIT_REQUESTS`, `RATE_LIMIT_TRAINING`, `RATE_LIMIT_ASSISTANT` | Abuse-control request limits. |
| `STORAGE_DIR` | Persistent source/model file location. |
| `MAIL_API_KEY`, `MAIL_FROM`, `PUBLIC_BASE_URL` | Optional email-verification configuration. |

Native URL format:

```text
postgresql+psycopg://USER:URL_ENCODED_PASSWORD@HOST:PORT/DATABASE
```

Generated passwords are URL-safe. URL-encode manually supplied passwords. Remote production PostgreSQL requires `sslmode=require`, `verify-ca` or `verify-full`; prefer `verify-full` with the provider's trusted CA and matching hostname. Include any required `sslrootcert` path using the provider's documented configuration. `require` encrypts transport but does not provide the same hostname verification as `verify-full`. Preserve TLS verification during troubleshooting. Use the provider's host/port/database/application credentials, not assumed local defaults. Configure `COMPOSE_DATABASE_URL` separately when Docker should use that remote database.

AI configuration examples use field names, not credentials:

```text
OPENAI_API_KEY=
OPENAI_MODEL=
GEMINI_API_KEY=
GEMINI_MODEL=
ANTHROPIC_API_KEY=
ANTHROPIC_MODEL=
```

Create an account with the provider you intend to use, enable API access/billing as required, generate a private API key and select a model ID listed as available to that account. OpenAI, Google Gemini and Anthropic use their corresponding fields above. For a compatible provider set `COMPATIBLE_API_KEY`, its exact HTTPS API root in `COMPATIBLE_BASE_URL` (often ending `/v1`, without `/chat/completions`) and `COMPATIBLE_MODEL`.

Fill at least one provider's actual key and usable API model ID locally, then restart the server. A coding application's model labels are not guaranteed API identifiers. Keys stay on the server. Check the provider's official account/API documentation for supported IDs and billing; no account access or commercial answer-quality result is bundled.

## 6. Import and review data

Open More tools, Data Manager and load the starter cohort. Its 800 public ClinicalTrials.gov records and original source hashes are preserved. The five software-test fixtures are a separate dataset and cannot support scientific prediction or training.

Canonical imports require `nct_id` and `title`. Useful model fields are `phase`, `study_type`, `enrollment`, `number_of_arms`, `primary_outcomes`, `secondary_outcomes`, `criteria_count`, `brief_summary` and `eligibility_criteria`. Existing CSV/JSON, Excel, Parquet and documented registry/import workflows remain available.

Review quality, missingness and source hashes before analysis. Invalid numeric/date fields and duplicate study IDs cause a validation error without a partial import. Preserve raw AACT files unchanged. Arbitrary uploaded model binaries are not trusted saved models.

Duration fitting requires completed studies with precise start/completion dates and established ACTUAL completion outcomes. Estimated, imprecise, inverted, missing or nonpositive outcomes are excluded. Strict pretrial inference additionally needs consumed-feature availability timestamps.

Recruitment graphs require actual supported screening, eligibility, enrollment, follow-up/completion or site fields. Planned enrollment does not establish screening, retention or dropout counts. Absent fields remain unknown.

## 8. Saved-model prediction

Open Prediction Studio, choose Duration or Phase consistency, choose an approved saved model, select an evidence mode and Predict now. Saved preprocessing/models run on up to 100 validated records. Prediction does not trigger training.

Select a returned study to inspect values, intervals, explanation, source/model hashes and provenance. The phase pathway and prediction journey appear after actual evidence returns. Guided scenes explain these returned source/model/results; they do not invent phase transitions. Previous prediction runs can be reopened. Export CSV/evidence JSON or print to PDF.

Retrospective mode supports historical screening with source limitations. Strict pretrial mode checks supplied feature timestamps against the prediction cutoff; missing or late timestamps block the record.

Prolonged-duration probability concerns the training-defined duration threshold, not clinical success or delay relative to an operational plan. Split-conformal intervals may be unbounded or unavailable. The phase classifier estimates a phase label, not advancement probability.

## 10. Scenarios and planning

Open What-If Lab from More tools and choose a study and available model branch. Blank overrides preserve source fields. Changed fields apply only to the hypothetical copy; the original dataset remains unchanged.

Supply all planning assumptions: sites, participants per site per month, startup months and follow-up months. Name and run the scenario. Compare base/model results, changed/model results, PCI differences and explicit planning totals. A constant baseline can legitimately produce no prediction change.

```text
Recruitment months = enrollment / (sites × monthly recruitment rate per site)
Planning total = startup + recruitment + follow-up months
```

This is arithmetic using your assumptions, not a trained recruitment-risk forecast. Protocol perturbations are not causal evidence. The Scenarios workspace retains saved comparisons and provenance. Network errors never trigger a substitute prediction.

## 11. Train, compare, approve and activate

Owners can open More tools → Experiments, review readiness, select Include CatBoost, choose Standard search or Expanded CatBoost search and Run experiment. Actual run states and completed manifests/held-out predictions are retained. Researchers/reviewers/viewers cannot train or activate.

Standard search (the default/basic mode) preserves the v5.2.0.2 CatBoost parameters and two ordered depths, 4 and 6. Expanded search evaluates eight ordered combinations per task: depths 4/6, L2 values 3/10 and 120/300 iterations. It needs more fitting time and does not guarantee better held-out results. CatBoost must be enabled separately. One-class training can use the existing prior fallback and records only searches actually performed.

Each candidate fits preprocessing and estimator on training records only. Duration selection uses tuning RMSE; risk selection uses tuning Brier. Calibration and test records do not fit/search candidates. Exact ties keep the first declared candidate. The manifest records configurations, actual/effective parameters, trial scores, selected indices, split counts, tie rule and CatBoost version. No validation refit or automatic activation occurs.

The nine existing branches are median/prevalence baseline, structured/text/multimodal linear models, Extra Trees, Random Forest, Gradient Boosting, Histogram Boosting and weighted late fusion. Opt-in CatBoost adds a tenth candidate and native additive TreeSHAP.

Preprocessing fits training records only. Tuning, calibration and test splits retain distinct roles; date groups and outcome-availability purging protect direct split separation. Compare duration MAE/RMSE and classification Brier/AUROC/average precision. Undefined metrics remain unavailable.

The preserved v5.2.0.2 frozen-cohort comparison used 800 inputs, 312 eligible precise ACTUAL outcomes, 123 temporal exclusions and retained splits of 105 training, 9 tuning, 11 calibration and 64 test records. The median baseline remains the duration validation winner. CatBoost is a candidate capability, not an activated accuracy claim. Detailed evaluation evidence is included in `docs/v5202-evidence/`.

The v5.2.0.3 authentic 800-record expanded comparison kept the prior basic run's splits and recommended `text` for the risk branch in both runs. CatBoost duration validation RMSE was `583.6089521513263` and test RMSE was `454.49926978644356`, unchanged from basic. Tuning Brier changed from `0.08050878086835794` (basic) to `0.07927376884169636` (expanded), while held-out test Brier changed from `0.11011105593329391` to `0.11806014427359898` (worse). These exact reported results do not support an overall accuracy improvement. The candidate was not activated and approved artifact selection remains unchanged. Read the current release evidence for complete manifests and methodological limits.

After completion, open Models. Inspect source, metrics, hashes, eligibility and limitations. Owner approval is required before activation. Training alone does not replace the active model. Branch selectors list branches present in the approved artifact; CatBoost appears after a compatible candidate is approved/activated. Do not repeatedly tune on the test set.

## 12. Protocols, sources and formulas

Protocol Evidence imports supported PDF/text, extracts text and links fields to page/section evidence. Inspect excerpts before using extracted values. Owners/clinical reviewers can review or correct evidence; researchers can import documents. Scanned PDFs without extractable text need a supported separate text/OCR workflow.

Version comparison identifies added/removed text. Amendment-risk prediction is unavailable without suitable labels and validation. The advanced reviewed rubric is a separate user-defined calculation.

Research sources integrates ClinicalTrials.gov, PubMed and openFDA. Save useful results to the project evidence library. Live services need internet and can report availability errors. Complexity Lab and Formula Studio explain fixed PCI weights, ceilings, rounding and missing-data policy.

Phase Academy, Phase Model, Research Hub and Validation Lab retain their existing research/educational workflows and saved evaluation evidence.

### Fixed-reference PCI, with explicit assumptions

```text
PCI = sum(weight_i × clip(value_i / ceiling_i, 0, 1))
```

| Component | Input field | Ceiling | Weight |
| --- | --- | --- | --- |
| Eligibility burden | `criteria_count` | 40 | 25 |
| Primary outcome burden | `primary_outcomes` | 10 | 20 |
| Secondary outcome burden | `secondary_outcomes` | 20 | 20 |
| Arm complexity | `number_of_arms` | 8 | 15 |
| Enrollment burden | `enrollment` | 1000 | 10 |
| Text complexity | `text_complexity` | 20 | 10 |

Sum unrounded components, then round the total to two decimals using exact decimal half-up. Categories use the rounded score: Low below 40, Medium 40–70 inclusive, High above 70. Missing, invalid and nonfinite inputs contribute zero and are disclosed, so incomplete records may be understated. Finite negative values clip to zero. These are descriptive research assumptions, not clinically validated thresholds or probabilities. Exploratory custom weights and training-relative research PCI retain separate method labels.

A formula-only check sets each input to half its ceiling, producing 50 points. That arithmetic example is not a trial record or clinical result.

## 13. Assistant configuration and feedback

Use Settings, Assistant for provider/profile, enable switch and budgets. A daily quota of 0 means no daily application quota; request and provider limits still apply.

New projects store daily application quota **0**, meaning no daily application quota. Existing explicitly configured quotas remain unchanged; older omitted settings can retain the legacy fallback. Provider billing/rate/context/output ceilings, project budgets and request abuse controls still apply. This is not unlimited provider usage or an accuracy guarantee.

Open Assistant, choose a study or dataset context and send a question. Replies stream as readable Markdown, including lists/tables/code. Sources identify actually supplied references. Copy/export preserves answers. Errors do not create invented replies.

Context includes actual cohort quality, selected-study fields, saved predictions, active-model evaluation, protocol excerpts and relevant saved evidence. Verify answer claims against their sources. Commercial provider access needs your own usable credentials; automated provider and UI streaming checks use local test responders.

Useful/Needs review records feedback against a completed message owned by your account. An owner uses Settings, Feedback review to approve an evidence-backed correction. Approved guidance can inform later project prompts. Pending feedback is not an instruction and source measurements take precedence.

This is reviewed context improvement. Model weights change through evaluated training and owner approval; feedback does not prove increased accuracy or automatic retraining.

## 17. Backup and deployment

Back up PostgreSQL and research-file volumes together. Database records do not contain all PDFs/CSVs/model binaries. Use your provider's backups or PostgreSQL `pg_dump`; keep your private environment secure.

Deployment requires HTTPS, authenticated session mode, production values, TLS PostgreSQL, persistent storage and explicitly trusted reverse proxies. The release validates a development/container workflow, not a certified production or clinical deployment.

For a previous SQLite development installation, export/import source datasets and retain hashes. This release does not automatically migrate SQLite or ship old runtime databases.
