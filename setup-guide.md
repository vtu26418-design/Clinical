# veltech-ams-mini 2.2.0 — upgrade and Android install

This release targets `https://app.veltech-mini-ams.me`. It includes the new mobile login and launch animation, combined campus logo, locally bundled Manrope font, one live Home reminder hub, separate mobile settings views, redesigned notifications and a real signed Android APK. The existing application, database and campus accounts are retained.

## Upgrade your existing AWS installation

1. Back up your database, media volume, `.env`, `.private` and server/proxy configuration. Keep the same database address, `CAMPUS_LINK_KEY`, `CAMPUS_SERVICE_KEY`, session keys and account records. Do not run a fresh setup over existing private files or replace them with example credentials.
2. Extract the full bundle. The `veltech-ams-mini` folder is the source project; the separate `android-release` folder is the already verified public Android release. Place the new source in your normal AWS release directory and retain the existing private configuration and persistent volumes.
3. Review [AWS-CLOUDFLARE-MOBILE.md](AWS-CLOUDFLARE-MOBILE.md). Set the real HTTPS origin in your existing configuration, keep secure cookies, use Cloudflare Full (strict), and trust only the actual reverse proxy address/subnet. Never cache private `/api/` responses. Do not disable WAF protections for the whole site.
4. Rebuild/start using your existing deployment's Compose files. For the standard PostgreSQL stack:

```bash
docker compose -f compose.production.yaml -f compose.postgres.production.yaml up -d --build
```

Use the files you already deploy; do not switch from an existing MongoDB/Atlas deployment to PostgreSQL as part of this UI update. The default Windows Docker setup uses:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Setup.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\Start.ps1
```

On an existing configured installation use `Start.ps1`; preserve `.private` and your original database. No Ubuntu installation is required. See the earlier detailed V2-UPGRADE.md guide for storage, SMTP and normal deployment configuration.

## Publish the included Android release in the app

The full bundle's `android-release` folder contains only public release files: the checksum-named APK and `release.json`. It contains no signing key/password. It was generated by the publisher after independently checking the binary's signature, package, version and alignment. You can copy these files without installing the Android SDK on AWS.

In the existing `.private/campus.env` (or equivalent server configuration), use:

```dotenv
CAMPUS_APK_DIRECTORY=/app/media/app-releases
CAMPUS_ANDROID_PACKAGE_ID=in.velstudents.veltechams
CAMPUS_ORIGINS=https://app.veltech-mini-ams.me
CAMPUS_COOKIE_SECURE=true
```

`CAMPUS_APK_DIRECTORY` is a path inside the campus container, not your Windows host path. Using your usual Compose project/files, create the directory and copy the supplied public release folder into the persistent media volume:

```bash
docker compose exec -T campus mkdir -p /app/media/app-releases
docker compose cp ../android-release/. campus:/app/media/app-releases/
```

The example assumes you run the command from the extracted `veltech-ams-mini` directory. If your release folder is elsewhere, adjust only the source path. Ensure the running campus user can read the copied files. Restart/recreate the campus service with your normal deployment command after changing its environment. Every campus replica must read the same persistent release directory.

Open `/api/campus/app-release` on the deployed site; it should report `available: true`, version `2.2.0` and code `20200`. Metadata and APK downloads are intentionally public so a new student can install before signing in. Academic data and accounts remain authenticated. The installer checks the APK checksum before saving; a changed/stale release requires checking again.

In the app open Settings → Install & updates → Download Android APK. Open the saved `.apk` in Android Downloads and confirm the OS installation prompt. Android may ask permission to install from your browser. A website cannot silently install an APK. Web app installation is a separate secondary option, including Safari Add to Home Screen for iPhone. Android requires version7 or newer and a compatible browser.

# Upgrade 2.2 on AWS behind Cloudflare

The public origin is `https://app.veltech-mini-ams.me/`. These are manual deployment instructions; this release performs no AWS writes, DNS changes, SMTP sends or production uploads.

1. Back up persistent database/media and existing environment configuration through your normal private process. Retain session-cookie keys, academic-link encryption keys, VAPID keys, database identity and TLS keys. Restore the same persistent volumes on upgrade. Do not replace secrets with values from example files. Keep the preceding image for rollback and never roll back the database by deleting volumes.
2. Cloudflare SSL/TLS must use **Full (strict)**. The AWS origin needs a valid certificate matching this hostname (a trusted public certificate or properly installed Cloudflare Origin CA for Cloudflare-to-origin use). Do not use Flexible mode. Restrict the AWS security group/origin ingress to the expected proxy path; never expose campus 4100, academic 8000 or databases publicly. Cloudflare Origin CA is not trusted by ordinary direct browsers; use the Cloudflare public hostname.
3. Preserve the existing reverse-proxy topology. The supplied Nginx edge terminates HTTPS and overwrites client-supplied `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto` and `Forwarded`. `CAMPUS_TRUST_PROXY` must contain only your actual immediate proxy address/subnet; the compose default `172.29.240.2/32` corresponds to its static Nginx address. Do not set trust proxy to true, `*`, or all Internet addresses. If Cloudflare client-IP restoration is needed, configure Nginx `set_real_ip_from` for the current official Cloudflare ranges and `real_ip_header CF-Connecting-IP`; the origin must accept those headers only from Cloudflare. Never accept a caller's `CF-Connecting-IP` at a directly exposed origin. Verify secure cookies, rate limits and client-IP audit behavior with your real ingress chain.
4. Add explicit Cloudflare cache bypass rules for `/api/*`, session/login/logout, authenticated data, files/downloads and `/api/campus/app-release*`. Bypass any “Cache Everything” rule and preserve `Cache-Control: no-store` and cookies. Exclude authenticated API calls and APK attachment downloads from challenge/HTML substitution rules that would turn binary or JSON responses into a challenge page. Keep existing academic/account authentication and API authorization in place. APK metadata and download endpoints are intentionally public and contain no private account information; do not add a sign-in gate to them. Do not cache student data at the edge. Static content-hashed assets can use normal immutable caching; keep HTML, service worker and manifest revalidatable so installed clients see upgrades.
5. Deploy the 2.2 source/image through your existing reviewed compose process. Validate configuration first; retain `.env.production` privately. Do not run `down -v`. All campus replicas must use the same media/release directory and session keys. The stock production compose mounts `campus_media:/app/media`; add only public APK files under `app-releases` there and set `CAMPUS_APK_DIRECTORY=/app/media/app-releases`. Signing keys stay outside Docker build contexts and media volumes. Follow [ANDROID.md](ANDROID.md) for local verification/publication.
6. Deploy the generated **public** `.well-known/assetlinks.json` for the release fingerprint using the exact public route described in [ANDROID.md](ANDROID.md). Ensure no login, redirect, bot challenge or SPA HTML fallback is returned. Do not deploy an old/debug/Play upload-key fingerprint in place of this actual sideload signing certificate. If Play App Signing is introduced later, add the actual Play app-signing certificate separately.
7. After deployment, verify public HTTPS/manifest/service-worker/assetlinks and an authenticated app session. The release metadata API should show 2.2.0/20200 and the expected checksum; downloading the APK should return HTTP 200, `application/vnd.android.package-archive`, attachment disposition, no-store and the same SHA-256. Verify that both `/api/campus/app-release` and the current `/api/campus/app-release/apk?sha=...` work without sign-in and return only public release information or the distributable APK. Separately verify that logged-out requests to protected academic/account APIs are rejected according to their existing auth policy, never served from Cloudflare cache. Check private data with two independent sessions to confirm no cross-user edge caching. Test installation/update with Android confirmation and actual browser domain verification. Do not claim phone acceptance based solely on HTTP checks.

The2.2 website and the APK are separately deployed: a locally built APK opens whatever version is currently live at its configured origin. The Install & updates page correctly reports release unavailable until the verified APK directory is mounted and metadata is published. Updating the website alone cannot silently install an APK on users' phones.

## If Cloudflare returns 403 / error 1010 for domain verification

A later read-only release probe saw Cloudflare HTTP 403 with `error code: 1010`, including the Asset Links path. Android/browser domain-verification requests must be able to read this public JSON without a browser challenge. Review the corresponding Cloudflare Security Event first. Where Browser Integrity Check or a managed challenge is the cause, create an exception/configuration rule scoped to the exact hostname, exact metadata path and GET/HEAD only, for example:

```text
(http.host eq "app.veltech-mini-ams.me" and
 http.request.uri.path eq "/.well-known/assetlinks.json" and
 http.request.method in {"GET" "HEAD"})
```

Disable only the specific Browser Integrity Check/challenge feature responsible for that public metadata route, using the appropriate Cloudflare configuration/WAF rule. Keep the rest of the WAF, API authentication and rate limits enabled. Do not allow all request paths or disable all Cloudflare security to fix domain verification. Origin firewall rules should continue allowing only the expected ingress. After the exception and JSON deployment, verify HTTP 200/application/json from the public hostname, no redirect/challenge/HTML body, then request Android/browser re-verification. A signed APK can still be installed while this manual domain-association fix is pending.


# Android release: Windows, Linux and CI

The approved origin is **https://app.veltech-mini-ams.me/**. The release configuration is `android/config.release.json`: package **in.velstudents.veltechams**, version **2.2.0**, Android versionCode **20200**. The user confirmed there is no earlier APK, so this release establishes a new signing identity. Preserve that identity for every update.

Minimum Android version is 7.0/API 24: the pinned Browser Helper 2.7.4 requires API 24. This is a Google Bubblewrap Trusted Web Activity (TWA), using the deployed HTTPS app in a supported browser, normally Chrome. It does not bundle the website or store student credentials in native code. Website changes require deploying the web release. The launcher icon can be generated from the new local `frontend/public/icons/app-512.png` before that web release is deployed. Browser camera and notification permissions still require real phone testing.

There are two separate results: APK signature/identity/alignment verification, and live domain association. A signed APK is installable while association is pending; browser controls may remain visible until the matching Digital Asset Links statement is deployed and the browser verifies it. Neither a successful build nor a live JSON check proves that installation, AMS, camera or push works on a physical phone.

## Local prerequisites

Use Node >=22.12, JDK 17 or 21, Android SDK platform 36, Build-Tools 36.1.0 and platform-tools. Android Studio's SDK Manager installs them on Windows; official command-line tools also work on Linux/macOS. Set `JAVA_HOME` and `ANDROID_HOME` to the real installation directories. Review and accept the SDK licenses. The project pins Bubblewrap 1.27.0, Android Browser Helper 2.7.4, AGP 8.9.1 and Gradle 8.11.1. The wrapper JAR and Gradle distribution have pinned official checksums. These pinned tools provide repeatable build steps; byte-identical APK output is not promised.

```sh
npm --prefix android ci
npm --prefix android test
node scripts/android-prepare.mjs --config android/config.release.json --dry-run
node scripts/android-prepare.mjs --config android/config.release.json --local-icon frontend/public/icons/app-512.png
```

The generator checks public DNS, HTTPS, the manifest launch route, service worker and icon. It never disables TLS verification. `--local-icon` explicitly uses the release's local PNG for native icons while retaining the checked public deployment origin. Use it when the deployed website still has the preceding version's icon. Omitting it uses the live icon. Generated files are replaced on preparation; change source scripts/configuration instead of editing them by hand. `android/config.example.json` intentionally contains an invalid placeholder; `--config android/config.release.json` selects the real origin.

## Signing identity and backup

**Do not generate a replacement key for an update.** The release generated in this session uses a private 3072-bit RSA PKCS12 keystore outside the project at `/workspace/.campus-mobile-v22/android-private/velstudents-release.keystore`; alias `velstudents`. Its strong random password is separately stored in that same protected session directory as `keystore-password` (mode 0600, parent 0700). Neither file belongs in source, ZIPs, screenshots, GitHub artifacts, public release storage or logs. They are deliberately absent from the delivery archive.

Before this workspace expires, the project owner must transfer the keystore through their private authenticated workspace access into encrypted backup storage, and put the password in a private password manager. Maintain a second encrypted backup, restrict access and verify that `keytool -list` can read the restored key. Keep the password separately from the backup. This document does not contain the key or password. A public signed APK or fingerprint cannot recover a lost private key.

On your computer, restore this existing key under `android/private/velstudents-release.keystore`, or set `CAMPUS_ANDROID_KEY_DIRECTORY` to the external protected folder containing it. The config allows only a keystore filename, never arbitrary credential paths or passwords. Do not commit `config.local.json` if you use it for your own origin. Preserve existing deployment cookie/encryption/VAPID/academic-link keys during upgrades.

For a genuinely new independent app only, create its own identity once (the delivered app already has one):

```sh
keytool -genkeypair -storetype PKCS12 -keystore android/private/velstudents-release.keystore -alias velstudents -keyalg RSA -keysize 3072 -validity 10000
```

Answer the prompts; never put a password directly in a command argument or JSON file.

## Build on Linux/macOS

Set `ANDROID_HOME` and `JAVA_HOME` to your installations. Supply signing passwords only in the local process environment; the following Bash prompts hide input and clear the variables after building:

```bash
read -rsp 'Keystore password: ' CAMPUS_ANDROID_STORE_PASSWORD; echo
export CAMPUS_ANDROID_STORE_PASSWORD
export CAMPUS_ANDROID_KEY_PASSWORD="$CAMPUS_ANDROID_STORE_PASSWORD"
node scripts/android-build.mjs --config android/config.release.json
unset CAMPUS_ANDROID_STORE_PASSWORD CAMPUS_ANDROID_KEY_PASSWORD
```

`CAMPUS_ANDROID_KEY_DIRECTORY` selects the external key folder when needed. In a managed execution environment, use its configured HTTP(S) proxy and CA. Node 24 supports `NODE_USE_ENV_PROXY=1` with `NODE_EXTRA_CA_CERTS` pointing to the supplied certificate. Java/Gradle require their own proxy properties and a truststore extending the standard JDK roots with the supplied CA; retain TLS checks. Use a writable `ANDROID_USER_HOME` and `GRADLE_USER_HOME` in restricted workspaces. These session-specific files belong outside the delivery. Do not solve network errors by disabling TLS, changing the origin to HTTP or bypassing the proxy.

A successful build produces only these public distribution outputs:

- `android/out/veltech-ams-mini-release.apk`
- `android/out/veltech-ams-mini-release.apk.sha256`
- `android/out/signing-receipt.json`

The build runs Gradle `assembleRelease`, 16 KiB zip alignment, Android `apksigner` signing and verification, checks the APK signing certificate against the selected keystore, checks its package/version/launchable activity, rejects a debug APK, and verifies final alignment. Its receipt includes the independently computed APK checksum and separate `domainAssociation` result. Add `--require-domain-association` to require a matching live association; if association is pending, the valid local APK is retained and the command exits nonzero for that gate.
