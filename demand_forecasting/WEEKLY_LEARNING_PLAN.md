# Month 1: Demand Forecasting & Inventory Optimization

This is one cumulative project, delivered as four weekly ZIP snapshots. Week 2 includes Week 1; Week 3 includes Weeks 1–2; Week 4 is the complete project. All archives use the folder `demand_forecasting`. The full-month ZIP contains the final code and all weekly learning guides. Use Python 3.12. All commands run from that folder.

The supplied code is a working reference implementation. Your learning tasks are to understand, reproduce, test and adapt it, then explain your own choices. Describe supplied starter code and your contributions honestly in the internship report. No fabricated dates, metrics, inventory observations or Git history are supplied.

## What the final system does
1. Validates daily store–item sales and records source hashes.
2. Audits sales and exports EDA tables/charts.
3. Creates historical lag/rolling/calendar features.
4. Compares naive and seasonal-naive forecasts with linear regression and Random Forest.
5. Selects by validation MAE, then reports later held-out test results.
6. Refits the selected method for future seven-day forecasts.
7. Computes explicitly assumed inventory scenarios, with CSV/JSON exports.
8. Provides a Streamlit dashboard, optional local FastAPI endpoints and a SQLite learning exercise.

## Data: what is included and where real data comes from
The bundled `data/raw/demo_sales.csv` has **5,840 generated practice observations**, eight series and 730 days per series. It is SYNTHETIC, generated by a fixed-seed Poisson simulation with assumed weekday effects and trend. Its metrics prove software behavior on a practice example; they are not retail findings. No API key or Kaggle account is needed to run it.

For your real internship analysis use:
- Recommended: [Store Item Demand Forecasting — Kaggle](https://www.kaggle.com/competitions/demand-forecasting-kernels-only/data). Create an account if needed, review the competition terms, and download historical `train.csv`. The separate competition test file has no sales labels and cannot be used to measure local forecast errors.
- Extension: [M5 Forecasting — Kaggle](https://www.kaggle.com/competitions/m5-forecasting-accuracy/data). This is larger, uses a different wide format, and needs an explicit transformation before this application's canonical CSV interface. Do not upload its unconverted wide table.

Expected CSV columns: `date,store,item,sales`; use YYYY-MM-DD dates, unique date/store/item keys, nonempty IDs, finite nonnegative units and continuous daily observations within each series. Extra columns are ignored in this beginner implementation. Do not silently treat missing observations as zeros. Raw transactions need documented daily aggregation before ingestion; returns need an explicit treatment.

Save downloaded data as `data/raw/train.csv` (excluded from Git). Keep the original unchanged. To make a bounded subset, run this in a Python console/notebook from the project root:

```python
import pandas as pd
raw = pd.read_csv('data/raw/train.csv')
subset = raw[raw['store'].isin([1, 2]) & raw['item'].isin(range(1, 11))]
subset.to_csv('data/raw/retail_subset.csv', index=False)
```

Then run, after reaching the corresponding week:
```bash
python -m src.cli prepare --input data/raw/retail_subset.csv --output reports/real_week01
python -m src.cli baseline --input data/raw/retail_subset.csv --output reports/real_week02
python -m src.cli train --input data/raw/retail_subset.csv --output reports/evaluation/retail --models models/retail
python -m src.cli forecast --input data/raw/retail_subset.csv --model models/retail/selected_model.joblib --output reports/evaluation/retail/future.csv
```

Record dataset URL, acquisition date, terms, columns, filtering decisions and exclusions in your report. The code records byte hashes but cannot independently certify uploaded-data licensing or authenticity. In Week 4 select **Upload sales CSV** in the dashboard. Start with two stores and no more than ten products. The dashboard limits scope to 20 series and 100,000 selected rows.

The Kaggle starting dataset supplies no observed inventory, supplier lead times, stockout flags, price or promotion columns. Do not invent these fields. Inventory inputs in this application are explicitly labelled what-if assumptions. Sales are a demand proxy and may be constrained by unavailable stock.

## Week 2 — Features, chronological splits and baseline forecasts
**Goal:** produce honest seven-day reference forecasts without future information.

**Topics:** trend/seasonality, forecast horizon and origin, lag features, shifted rolling statistics, calendar features, data leakage, chronological validation, naive/seasonal-naive baselines, MAE/RMSE/bias/WAPE.

**What to do and how:**
1. Read `src/forecasting.py` and run `python -m src.cli baseline`.
2. Inspect `reports/week02/baseline_report.json` and the per-origin predictions CSV.
3. Manually verify one seven-day seasonal-naive forecast repeats the previous week's corresponding values.
4. Inspect lag-1/7/14 and rolling means in notebook 02. Each series has its own history and every target is excluded from its features.
5. Understand the split: last 28 days are test; preceding 28 are validation; earlier rows are training. Every series needs at least 42 initial training days (98 total days for this workflow).
6. Evaluate four seven-day validation origins. Within a horizon later lags use earlier predictions; observed actuals become available only between origins.
7. Try a zero-demand example and explain why WAPE is null when actual totals are zero. Final test outcomes are not inspected in this stage.

**Day plan:** Day 1 time-series concepts; Day 2 lags; Day 3 rolling features/leakage; Day 4 baselines; Day 5 time splits; Day 6 evaluation; Day 7 mid-review preparation.

**Learn on YouTube:** [codebasics: forecasting channel search](https://www.youtube.com/@codebasics/search?query=time%20series%20forecasting), [StatQuest: training/validation/testing channel search](https://www.youtube.com/@statquest/search?query=training%20validation%20testing).

## Week 3 — Modeling, evaluation and inventory scenarios
**Goal:** choose a forecasting method using validation evidence and document inventory assumptions.

**Topics:** supervised regression, linear regression, Random Forest, categorical encoding, scaling/pipelines, overfitting, validation-based model selection, recursive multi-step inference, persistence/checksums, inventory position, safety stock, service-level assumptions, reorder point and pack rounding.

**What to do and how:**
1. Run `python -m src.cli train`. Four methods are compared: naive, seasonal naive, linear regression and Random Forest.
2. Inspect `reports/evaluation/demo/manifest.json`. Selection uses validation MAE exclusively; test results are computed after that choice. The same initial training-only fitted models are evaluated across validation/test origins.
3. Inspect actual per-row validation/test prediction CSVs. Calculate one model's MAE manually or with pandas. A baseline is allowed to win.
4. Read notebook 03 and change one justified model setting in a separate experiment. Do not repeatedly tune against the final test set.
5. After evaluation, the selected approach is refitted on all known history for serving. Its future predictions are not an independently validated performance claim.
6. Run `python -m src.cli forecast` and inspect `reports/evaluation/demo/new_forecast.csv`.
7. Run `python -m src.cli inventory --store 1 --item 1 --lead-days 3 --on-hand 20 --daily-std 5`. These numbers are explicit scenario assumptions, not real stock observations.

**Inventory equations:** inventory position = on hand + outstanding orders − backorders; reorder point = lead-time forecast demand + safety stock; order toward lead-plus-review forecast demand + safety stock when the reorder trigger is met. Round up to pack size and minimum order when supplied. Safety stock uses z × daily demand SD × sqrt(fixed lead time), assuming independent daily demand and a normal approximation. A desired service level is not a validated guarantee. Lead-plus-review days cannot exceed the available forecast.

**Day plan:** Day 1 regression; Day 2 Random Forest; Day 3 validation comparison; Day 4 inference/persistence; Day 5 inventory calculations; Day 6 tests/error analysis; Day 7 results/assumptions report.
